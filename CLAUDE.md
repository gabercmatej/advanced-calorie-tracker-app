# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

CalAI is an AI-assisted calorie/macro tracker built with Expo + React Native, targeting **iOS, Android, and web** from one codebase. Expo SDK 57, React Native 0.86, React 19, TypeScript strict mode.

## Commands

```bash
npm run check           # tsc (app) + tsc (tests) + unit tests — the main gate
npm test                # unit tests only
npx expo start          # dev server; press i (iOS), a (Android), w (web)
npm run ios | android | web
npx tsc --noEmit        # type-check (primary correctness gate — there is no test suite)
npm run lint            # expo lint (eslint-config-expo)
npx expo export --platform web   # full-graph bundle + static render; best "does it build" check
```

Verify changes with `npm run check` (app types, test types, then the suite). The tests run on `node --test` with Node's native TypeScript stripping — no jest, no new dependencies — and cover the pure logic in `src/lib/` plus the hand-written food and recipe corpora, where the failure modes are silent data errors rather than crashes. `scripts/test-alias-hooks.mjs` teaches the runner the `@/*` alias; test files are typechecked separately via `tsconfig.test.json` so Node's globals stay out of the app's type space. For anything touching the module graph or routing, also run `npx expo export --platform web` (renders every route and also regenerates the typed-routes file at `.expo/types/router.d.ts` — run this, or `npx expo start`, after adding/renaming a route or tsc will report stale route-type errors for the new path).

## Architecture

**Routing (Expo Router, file-based).** Routes live in `src/app` (not the repo root — `src/app` is the router root). `typedRoutes` is on, so `href`/`Link` targets are type-checked against actual route files.

- `_layout.tsx` mounts every provider (see below), waits for both `AuthContext` and `DiaryContext` to hydrate, and holds the splash screen until then.
- Root-level `<Stack.Protected>` branches on `session` (from `AuthContext`):
  - **Signed out** → `(auth)/` group: `welcome.tsx` (Get Started / Sign in) → `onboarding.tsx` (the multi-step plan wizard) → `sign-in.tsx`.
  - **Signed in** → `(tabs)/` group (Home / Progress / Food / Profile) plus modal routes: `add.tsx` (the fused food logger — see below; accepts an optional `?date=` param to log against a past day), `log-weight.tsx`, `entry/[id].tsx` (edit/delete a logged food). There is no separate day-detail screen — tapping a day in the Home week-strip or the Progress calendar calls `setSelectedDate` so Home re-points at that date. There is likewise no recipe-detail route — recipe cards expand in place.
- `(tabs)/_layout.tsx` renders the JS `Tabs` navigator plus a floating "+" button (not a tab) that opens `add.tsx`.

**State is split across five contexts, composed in `_layout.tsx`.** All persist to AsyncStorage via `src/lib/storage.ts` (namespaced keys in `StorageKeys`) and hydrate on mount behind a `ready` flag so hydration never clobbers storage with defaults.

**Storage is local-first; Supabase is a mirror, never a replacement.** `DiaryContext` hydrates from AsyncStorage *before* touching the network, always writes to it, and — when Supabase is configured and signed in — reconciles with the cloud through the pure functions in `src/lib/merge.ts`. A merge is a union: anything present on one side survives, collisions resolve to the newer `updatedAt`, and the only way a row is ever removed is an explicit tombstone (`StorageKeys.deletedEntries`) recorded when the user deletes something. `StorageKeys.syncOwner` records whose data is in local storage so a first sign-in adopts existing local history while a *different* account signing in stashes it rather than overwriting. Meal photos are deliberately **not** synced — they stay on the device, which is what keeps a year of logging inside Supabase's free tier. `src/lib/backup-format.ts` + `backup.ts` provide JSON/CSV export and a merge-only restore from Profile → Your data.

- `AuthContext` — local mock session (`session: Session | null`). "Continue with Google" and email sign-in both just create a `Session` object; there is no real backend yet. Gates the root stack.
- `DiaryContext` — the main domain store: `Profile` (goals, metrics, units, theme, notification pref), `FoodEntry[]`, `WeightEntry[]`, plus derived values (`entriesForDate`, `totalsForDate`, `streak`, `loggedDates`, `weighedDates`) and `recommendation` — an adaptive, muscle-sparing calorie/macro plan for cutters from `computeAdaptivePlan()` in `nutrition.ts` (null for maintain/gain goals), which drives the Progress screen's plan card. Screens never touch storage directly — they call `useDiary()`.
- `ThemeContext` (`ResolvedThemeProvider`) — maps `profile.theme` ('light' | 'dark' only) to the active scheme; `useTheme()` / `useGradients()` read through this, not directly off `useColorScheme()`.
- `FoodContext` — state for the Food tab: `pantry` (ingredient ids the user has), `favorites`, `hidden`, model-generated `library` additions, and the Ask `chat` transcript. Reads `useDiary()` at the point of use rather than duplicating diary data. Deliberately **not** part of the splash gate — the Food tab renders a skeleton while it hydrates, so start-up is unaffected.
- `CelebrationContext` — imperative `celebrate(message)` that mounts a full-screen reward animation (`components/celebration.tsx`); fired after logging food or weight.

**The AI runs behind a server proxy.** `src/lib/claude.ts` is the single transport, and it calls the `claude` Supabase Edge Function (`supabase/functions/claude/`) — never Anthropic directly. The function holds `ANTHROPIC_API_KEY` as a server-side secret, requires a valid Supabase session, and charges each call against a per-user daily limit via the `claim_ai_call` RPC. There is deliberately **no** direct-to-Anthropic fallback: one that reappeared whenever the proxy was unreachable would be the same exposure with extra steps. Nothing named `EXPO_PUBLIC_ANTHROPIC_*` should ever exist again — `EXPO_PUBLIC_` values are inlined into the bundle. Three features sit on the transport: `ai.ts` (`estimateFood`), `recipes.ts` (`suggestRecipes`), and `food-qa.ts` (`answerFoodQuestion`); keep the `FoodEstimate` return shape stable. `src/lib/__tests__/offline-boundary.test.ts` walks the import graph and fails if quick-logging or the food library can ever reach the transport.

**Fallbacks must be honest, not decorative.** Every AI path degrades, but only where the offline result is genuinely useful: `estimateFood` falls back to a keyword heuristic over `food-facts.ts` and sets `estimatedOffline` so the UI can say the photos were never analysed; `answerFoodQuestion` falls back to a deterministic answerer. `suggestRecipes` deliberately has **no** fallback and throws instead — every matching bundled recipe is already on screen, so a fallback would be a button that appears to work and doesn't. The Food tab hides the control entirely when `hasClaudeKey` is false.

**The food logger fuses evidence rather than switching modes.** `add.tsx` takes up to 4 photos, a description, and any number of scanned barcodes at once. Scanned products are **never** sent back through the model for re-estimation — `estimateFood` tells the model what was scanned so it doesn't double-count, asks it to estimate only the remaining food, and composes the final total client-side. Label-derived numbers therefore stay exactly as accurate as the label. A scan-only meal makes no model call at all. The per-component breakdown is stored on `FoodEntry.items` for display.

**The Food tab** (`(tabs)/food.tsx`) has two surfaces behind one `Segmented`. *Ideas* ranks `recipe-data.ts` (bundled ingredients + recipes) via `recipes.ts` — pantry coverage, fit to the day's **remaining** calories/protein, protein density, and a recency-weighted taste profile built from logged entry names. *Ask* is retrieval, not embeddings (Anthropic has no embeddings endpoint, and the corpus is a few hundred in-memory rows): `food-qa.ts` filters relevant entries, adds standing summaries plus `food-facts.ts`, and stuffs it into one call. Ask is strictly read-only — it never writes an entry.

**The adaptive engine is deliberately slow to change its mind.** `computeAdaptivePlan()` works from *smoothed* bodyweight (`src/lib/weight-trend.ts`), averages intake over the last fourteen **complete** days (today is excluded — a part-eaten day dragged the target down every morning), and fits the rate of weight change with **Theil–Sen** rather than least squares, because one water-weight spike on the final morning flips an OLS slope's sign. Observed maintenance is clamped to ±25% of the Mifflin-St Jeor formula and then *blended* with it in proportion to data quality (log coverage, number of weigh-ins, their span), so a thin or noisy fortnight barely moves the number. A final rate limit caps movement at 75 kcal per calendar day against a stored `planAnchor`. Unlogged days are averaged as if they looked like logged ones — never counted as zero — and the coverage gate is what stops that assumption being stretched. `src/lib/diet-break.ts` reviews long cuts and returns **advice only**; it never changes the target, precisely because the adaptive engine already lowers calories when the trend flattens.

**Food data lives in one corpus.** `src/lib/food-library.ts` is ~300 foods stored **per 100 g** with named portions on top, so any weight scales exactly. `food-facts.ts` is a per-serving *view* of it (they used to be two tables that drifted), feeding the offline estimate heuristic and the Ask surface; `factsForPrompt()` bounds how much of it reaches the model. Carbohydrate is **total carbohydrate, fibre included** (US convention) — mixing that with the EU convention is an invisible error, so it is asserted in tests. Fibre rides alongside the macros as `FoodEntry.fiber` rather than inside `Macros`: it has no calorie-split target, and `undefined` (unknown) stays distinct from `0`.

**Onboarding computes a real nutrition plan.** `(auth)/onboarding.tsx` is a linear wizard (sex → workouts/week → height → weight → birth date → goal → target weight/date → diet → review → animated "calculating" → plan → account) that builds a `UserMetrics` object and calls `computeGoals()` in `src/lib/nutrition.ts` (Mifflin-St Jeor BMR × workout-volume multiplier, then a deficit/surplus sized to hit a target weight by a target date if given, else a flat default). The wizard is a `StepId` state machine (`flow` array of steps + a `validators` map + a `StepBody` switch) — adding a step means adding the `StepId`, pushing it into `flow` (conditionally if situational), adding a `validators` entry, and adding a `case` in `StepBody`.

**Onboarding persists before the account exists.** The wizard writes the plan to storage the moment it computes one — at the `plan` step, *before* the account step — and saves its in-progress answers to `StorageKeys.onboardingDraft` on every change. This is not belt and braces: it is the fix for a real data-loss bug. Sign-up with email confirmation enabled returns success *with no session*, the old code read that as an error and returned early, and every answer died with the component. `signUpWithEmail` now returns a three-way `SignUpResult` (`signed-in` | `needs-verification` | `error`) so the difference is impossible to collapse again. The root layout gates the app on `session !== null && profile.onboarded`, so a confirmed account on a fresh device is sent to onboarding rather than into the tabs against a placeholder goal.

**Sync decisions are a pure function.** `src/lib/sync.ts` (`reconcile`) decides what a sync does — what survives, whose data is on screen, what to push, what to stash — and `DiaryContext` only performs the effects. That split exists because this is the code whose bugs silently destroy a diary, and only a pure function can be tested against first sign-in, account switching, offline edits, conflicts and deletes. The invariant it upholds: **no branch can lose a record that is not covered by an explicit tombstone.** Account switching stashes the outgoing user's data *and* restores this account's own stash, so an A → B → A rotation cannot strand what A logged offline.

**Weight is entered in integer tenths.** `src/lib/weight-input.ts` holds the arithmetic (`914` ↔ `91.4 kg`) and `components/weight-picker.tsx` is the one control — a draggable ruler at 6 px per tenth, ± buttons, and a typed field. Tenths are not fussiness: float snapping produces `82.10000000000001`, which then fails an equality check and rewrites the field mid-edit. The drag reads `gestureState.dx` from where the gesture began, never `locationX` (whose frame of reference changes the moment a finger crosses a child view — that was the old slider's jump), and the field is **never** `selectTextOnFocus`, which on web re-selects after every controlled re-render so typing "82" yields "2".

**Layering.** `src/lib/` is pure logic (nutrition math, storage, ai, image picking, notifications) with no React. `src/context/` composes lib into app state. `src/components/` are presentational and read colors via `useTheme()`. `src/app/` screens wire context to components. Import everything via the `@/*` alias (→ `src/`).

**Theming.** All colors/spacing/radii live in `src/constants/theme.ts` as light/dark token objects; components consume them through `useTheme()` (and `useGradients()` for the `LinearGradient` color arrays). Do not hardcode colors — add a token. The look is deliberately **flat**: a single emerald accent on near-black surfaces, with `brand` gradients kept tone-on-tone (a narrow emerald→emerald ramp, never a multi-hue rainbow). There is intentionally **no colored glow and no ambient/radial backdrop** — both were removed on purpose (per design direction); don't reintroduce them or a `Shadow.glow`-style helper. Text/icons sitting on an emerald fill use the `onTint` token (dark ink in dark mode, white in light), never a hardcoded `#FFFFFF`. `Screen` renders the standard header; pass its `brand` prop for the one-line "CalorieTracker AI" bar on the tab screens. `themed-text.tsx` / `themed-view.tsx` are the base primitives; `CalorieRing` and `WeightChart` are `react-native-svg`-based.

## Conventions

- Files are kebab-case; components/types are PascalCase; the `@/*` path alias maps to `src/`.
- Cross-platform is a hard requirement: prefer RN primitives and `Platform.select`; the JS `Tabs` navigator is used (not `NativeTabs`) specifically so tabs render identically on web. Any new dependency must work on iOS, Android, and web. `expo-notifications` calls are no-ops on web by design (guarded in `src/lib/notifications.ts`) — don't add web-only fallbacks for them.
- Use `npx expo install <pkg>` (not `npm install`) so versions stay compatible with the SDK.
- Dates are plain `YYYY-MM-DD` strings ("date keys"), manipulated via helpers in `src/lib/nutrition.ts` (`toDateKey`, `fromDateKey`, `addDays`, `daysBetween`, `weekOf`, `relativeDayLabel`) — don't reach for a date library.
- Weight/height unit conversion (`kgToLb`, `lbToKg`, `cmToIn`, `ftInToCm`, `formatWeight`, `formatHeight`) also lives in `src/lib/nutrition.ts`; `profile.units` ('metric' | 'imperial') drives which unit inputs/labels default to.
